# Implementation Status

This is the only project document that describes current repository behavior and completeness.

See [Exchange Rules](exchange-rules.md) for adopted and unresolved behavior. See
[Architecture](architecture.md) for the intended system design. Neither document proves that a
feature is implemented.

## Status definitions

- **Implemented**: the described behavior exists end to end for its stated scope and has relevant
  tests.
- **Partially implemented**: meaningful behavior exists, but important paths or guarantees are
  incomplete.
- **Parsed only**: an external command is recognized or normalized but has no complete business
  processing path.
- **Stubbed**: a type, function, component, or configuration exists but does not provide the intended
  behavior.
- **Missing**: no meaningful implementation exists.
- **Unverified**: code or configuration exists, but this review did not establish that it builds or
  runs successfully.

## Known correctness limitations

These are implementation findings, not exchange rules:

- FIX normalization performs no session/client-command hashing, global counter increment, or
  wall-clock timestamp capture. No replacement compatibility fields were retained because repository
  inspection found no production consumer. The unconsumed legacy bus JSON serializer was removed.
- The immutable FIX client resolver loads exact identities only at startup. Adding or changing an
  authorized identity requires a configuration change and process restart; authentication beyond
  QuickFIX's configured session identity is not implemented.
- Deferred TimeInForce and expiry behavior is deliberately rejected at FIX normalization. If an
  unsupported TimeInForce bypasses normalization, matching treats it as an invariant failure before
  book mutation.
- FIX cancellation normalizes positive exact-decimal `OrderID(37)` into `TargetOrderId`, resolves
  stable configured `ClientId`, and ignores `OrigClOrdID(41)` for order identity. No private FIX
  business response exists.
- The authoritative in-process admission index gates normalized FIX commands before sequencing.
  Its exact lifecycle binds the complete normalized command to the assigned sequence, and the
  in-process result consumer completes records from strongly correlated immutable batches.
  Identical in-flight waiting/coalesced client delivery and completed-result FIX delivery are not
  connected; private response mapping and FIX mappings for the adopted admission reasons are not
  implemented.
- Run-bound admission starts closed. Only the isolated controller opens its shared index after
  committed `Open` activation or resume; recovered startup remains closed in `Paused`, and failed
  or uncertain transitions do not open admission. Existing-record retransmission/conflict lookup
  precedes the gate check. Closed-gate decisions carry `ExchangeRunUnavailable`, including when the
  table is also full; open-gate capacity-only decisions retain their existing absent reason.
  Gate closure and reservation decisions share the index mutex and preserve
  all existing records/results. This is not the adopted ordered pause/drain barrier. The executable
  still uses the explicitly legacy unqualified index, which starts open without lifecycle control.
- The production admission index owns at most 100,000 unqualified records and is not connected to
  admission reconstruction. The isolated recovery function can reconstruct a run-bound completed
  index from the journal and replay results; the isolated startup controller owns it after recovery,
  but does not install it into the production admission path. The
  production path does not implement an immutable run capacity, lifecycle transition to
  `CapacityReached`, or retained-run lookup, and no assigned `ExchangeRunId` prevents a client
  command identifier from colliding across process-created state.
- Direct internal matching-engine submissions do not pass through admission. A new direct Cancel
  command against an already-terminal target deterministically returns `OrderNotActive`; sequencer
  construction requires an explicitly named internal admission-bypass tag for such paths.
- `FixTask::fromApp` uses one mutex-serialized admission-and-staging operation. Record allocation
  precedes nonblocking queue publication; a full staging queue returns `GatewayBusy`, removes the
  unexposed reservation, and increments no accepted-first-submission count. Gate closure cannot split
  reservation from staging; duplicate/conflict lookup still precedes availability and never queues
  another command. The obsolete gateway abandon-failure diagnostic was removed. A full sequencing
  ingress instead leaves one command pending in the single FixTask worker, which retries it before
  taking later staged work. After sequencing, the sole sequencer similarly retains one outbound
  command across matching-queue saturation. None of these capacity conditions has a client-visible
  FIX response, and multicast-bus publication after matching lacks equivalent acknowledgement.
- The one sequencer counter is unique and gap-free for commands processed within a tested process,
  but it starts from zero on every process start. No assigned or pipeline-integrated `ExchangeRunId`,
  journal, durable commit, or recovery qualifies those values, so a restart can create numerically
  identical identifiers without the adopted new-run lifecycle or fully qualified identity.
- No instrument partition router or partition workers exist. `InstrumentId` reaches the single
  matching engine, while the retained `shard_id` field is non-authoritative and zero for FIX input.
- `FixTask`, the sequencer, `MatchingEngine`, and the admission-completion consumer use the same
  polling idle policy: 64 yields, then exponential sleeps capped at 1 ms. Active progress resets the
  policy immediately. There are no queue notifications, configurable wait parameters, or coordinated
  shutdown.
- Trade, terminal, cancellation, and command-rejection outcomes enter the bounded in-process result
  boundary as complete immutable batches. The internal consumer correlates and completes admission,
  but completed-result FIX delivery, downstream external delivery, and market data remain absent.
- Per-command events use an exactly planned, dynamically allocated vector, and NewOrder enforces the
  adopted 4,096-event limit before mutation. The first atomic in-process handoff and pre-accept
  backpressure stage is implemented, but accepted batches are not durable or recoverable.
